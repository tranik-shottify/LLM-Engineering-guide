PART 10

MLOps & LLMOps

The discipline of shipping, monitoring, and continuously improving language-model systems without breaking what already works.

The lifecycle: CI, CD, and continuous training

Production machine-learning systems run on three nested loops. Continuous integration validates that every commit still builds, type-checks, and passes unit and component tests. Continuous delivery guarantees that any green main-branch commit can be promoted to production in minutes, not weeks, with a one-click rollback. Continuous training (CT) is the loop distinctive to ML: as production data and labels accumulate, models are periodically retrained, evaluated against a frozen golden set, and — only if they win — promoted.

For LLM applications, "training" is rarely a from-scratch pretrain. It is more often an adapter refresh, a fine-tune of a small open-weights model, a retrieval index rebuild, or a prompt-pack update tied to a versioned artifact. The shape of the loop is the same: trigger → reproducible build → automated evaluation → gated promotion → observed in production → trigger again.

Experiment tracking and the model registry

Tracking captures every meaningful artifact of a run: hyperparameters, dataset version hash, code commit, environment specification, metrics, and the resulting weights or LoRA file. MLflow remains the de facto open-source choice; Weights & Biases dominates among research-heavy teams; Comet and Neptune occupy similar ground with different ergonomics. The tracking server feeds a model registry that assigns a versioned identifier to each artifact and records its lineage.

Treat models as you treat application code: semantic versioning, signed artifacts, immutable promotion (the v2.3.1 released last Tuesday is the v2.3.1 running in production today), and a clear traceability path from any production response back to the exact weights, adapter, and prompt template that produced it. The convention many teams settle on is major.minor.patch where major changes signal breaking output-shape or behavior shifts, minor versions encode capability gains on the same I/O contract, and patch versions cover hotfixes — typically prompt edits or retrieval index rebuilds with no model swap.

Model signatures and reproducible promotion

A signature pins down the input schema (text fields, allowed roles, max tokens), the output schema, the tokenizer, and the safety filters that wrap the model. A registry that enforces signatures rejects a v2.4.0 release whose output shape silently dropped a field — exactly the kind of regression that integration tests miss but downstream consumers catch the hard way.

Feature stores in an LLM world

Feature stores — Feast, Tecton, Hopsworks — were built for tabular ML, where the same engineered feature must be computed identically for offline training and online inference. For LLM workflows the picture is different. The "features" in a chat application are prompt context: user history, retrieved documents, tool-call results. Most of these are produced ad hoc per request and do not benefit from a feature store's caching and point-in-time-correctness guarantees.

Where feature stores genuinely help LLM systems is in structured side data that drives prompts: per-user preferences, account tier, recent purchases, computed user embeddings, churn-risk scores. When the same hot user attribute is consumed by both a recommendation model and an LLM-powered assistant, a single materialized source eliminates a class of skew bugs. Outside that case, plain caches and a retrieval tier usually suffice.

Pipeline orchestration and data versioning

The orchestrator landscape is crowded. Airflow remains the workhorse for batch ETL and scheduled retrains. Kubeflow Pipelines targets Kubernetes-native ML on GPUs. Metaflow, Flyte, Prefect, Dagster, and ZenML each take a different stance on Python ergonomics, typed I/O, and local vs cloud execution. Selection criteria worth weighing: type safety on task inputs, lineage tracking, retry granularity, support for GPU resource scheduling, and whether your team will tolerate a DAG-as-code authoring style or prefers decorators.

Data versioning closes the reproducibility gap that ordinary git cannot. DVC ties large blobs to commits via content hashes and a remote object store. lakeFS overlays a git-like branch/merge model on top of S3-compatible storage. Delta Lake brings ACID transactions and time-travel reads to Parquet on a data lake. The choice depends on whether your data is file-blob (DVC), bucket-scale (lakeFS), or table-shaped (Delta).

Containerization, runtimes, and cloud platforms

Inference workloads run in containers whether they live on a single GPU box or on a thousand-node cluster. Docker images encapsulate the runtime; Kubernetes schedules and scales them. On top of plain Kubernetes, KServe adds model-serving primitives — predict/explain endpoints, canary rollouts, autoscaling on inference QPS — and Knative contributes scale-to-zero for long-tail models that are queried infrequently.

Managed platforms — AWS SageMaker, GCP Vertex AI, Azure ML, Databricks — bundle most of the lifecycle into a single console with vendor-specific glue. They reduce the up-front engineering burden but increase coupling: a hand-rolled stack of MLflow + Argo + KServe is portable across clouds; a SageMaker pipeline is not. Most production teams end up somewhere on the spectrum: managed for training and registry, hand-rolled for the request path that touches the customer.

Monitoring and drift

Four flavors of drift matter in production LLM systems. Input drift: the distribution of incoming prompts shifts, a new use case appears, or a tenant onboards. Output drift: average completion length, refusal rate, or sentiment changes — often the first signal of a silent model swap upstream. Embedding drift: the distribution of retrieved-context embeddings shifts, signaling that the retrieval corpus is decaying or that user intent has moved. Hallucination rate: the share of outputs an automated grader flags as ungrounded or factually wrong, tracked over a rolling window against a fixed reference set.

Tools like Evidently, WhyLabs, Arize, and Fiddler compute drift statistics on streaming production data. For LLM-specific signals — token usage, tool-call success rate, eval pass rate by feature flag — the more common stack now is a purpose-built layer (LangSmith, LangFuse) feeding a general-purpose metrics store (Prometheus or a hosted equivalent).

Pitfall · Silent provider model swaps

Hosted model APIs sometimes update the model that backs an alias name without a major-version bump. A pipeline that pinned to gpt-4o rather than a dated revision can wake up to subtly different outputs and a quietly degraded eval score. Pin to dated revisions where the provider exposes them, and run a daily smoke eval against your golden set to detect the change within hours rather than weeks.

LLMOps specifics

Prompt registry and versioning

Prompts are code. Store them in a version-controlled registry — a directory of YAML files in your repo, a managed store like LangSmith or PromptLayer, or a dedicated table in your control plane — with the same review, diff, and rollback discipline you apply to source. Each prompt entry should carry an ID, a semantic version, the model and parameters it was tuned against, and the eval-suite scores at promotion. Changing a prompt without a version bump is the LLM equivalent of editing production SQL inline.

The eval harness in CI

Block pull requests on regressions the same way you block them on failing unit tests. The harness reads the proposed prompt or model bundle, runs it across a frozen suite of inputs (the golden set), grades each output with a deterministic checker or an LLM-as-judge, and compares aggregate scores to the current main-branch baseline. A regression beyond a small tolerance — typically two percentage points on key metrics — fails the job. Variance is real with LLM-as-judge; either run multiple seeds and average, or scope the gate to deterministic checks (exact match, JSON schema validity, regex, retrieval-recall@k).

name: llm-eval
on: [pull_request]
jobs:
  eval:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: { python-version: '3.12' }
      - run: pip install -e .[eval]
      - name: Run eval harness
        env: { OPENAI_API_KEY: "${{ secrets.OPENAI_API_KEY }}" }
        run: |
          python -m evals.run --suite golden --baseline main \
            --threshold 0.02 --report eval-report.json

The LLM gateway pattern

A gateway is a thin internal service that fronts every model call from your application. It centralizes authentication, per-tenant rate limiting, retries, fallbacks, prompt-template resolution, and structured logging. With a gateway, swapping a hosted provider for a self-hosted runtime is a config change, not a refactor; rolling out a 1 % canary on a new model version is a flag flip; and per-call cost attribution comes for free because every request flows through one place that knows which feature, tenant, and prompt-version it serves.

The feedback flywheel

Every interaction is a labeling opportunity. Capture explicit signals (thumbs-up/down, in-place edits, retries) and implicit signals (session length, copy events, downstream conversion) into a typed feedback store. Schedule a job that promotes the cleanest of these into evaluation suites or fine-tuning datasets. Over time, the gap between offline benchmarks and live production behavior narrows, because the suite itself is built from production reality rather than from synthetic prompts a research team hand-wrote eighteen months ago.

Token-level FinOps

Cost attribution starts at the gateway. Tag every request with tenant, feature, prompt_id, and model; write input and output token counts to a metering pipeline; aggregate into a daily cost ledger. From there: per-tenant showback dashboards, budget alerts when a feature crosses its envelope, and automatic fallbacks — when daily spend exceeds threshold, the gateway downshifts a non-critical feature from a frontier model to a smaller hosted model or to a self-hosted alternative.

The unit cost equation worth keeping at hand:

$$ C_{\text{req}} \;=\; \frac{p_{\text{in}}\, t_{\text{in}} + p_{\text{out}}\, t_{\text{out}}}{10^{6}} $$

where \(p_{\text{in}}\) and \(p_{\text{out}}\) are dollar prices per million input and output tokens and \(t_{\text{in}}\), \(t_{\text{out}}\) are the per-request token counts. Output tokens dominate for chat-shaped workloads; input tokens dominate for retrieval-heavy and long-context flows. Knowing which side dominates tells you whether prompt compression or output truncation pays off.

Multi-region deployment and rollback

For latency-sensitive workloads, model serving fans out across regions and traffic is steered by a global load balancer with weight-based or geo-based routing. Blue-green deployments hold two parallel stacks; traffic shifts atomically between them with a single weight change and a fast rollback. Canary deployments release a new model version to a small slice (often 1-5 %) and watch SLO and quality metrics before widening. Silent regressions — outputs that pass schema and latency gates but degrade end-user behavior — are the failure mode canaries are designed to catch; pair them with a held-out automated quality eval that runs on the canary slice continuously.

Observability and the OTel GenAI conventions

The shift toward standardized telemetry has been quick. OpenTelemetry's GenAI semantic conventions define a common shape for spans and metrics emitted by LLM applications: span attributes for gen_ai.system, gen_ai.request.model, gen_ai.usage.input_tokens, gen_ai.usage.output_tokens, and standard event names for prompt and completion payloads. The conventions are still evolving, but adopting them now keeps your traces forward-compatible and lets a single backend ingest data from multiple SDKs.

The application-layer tooling — LangSmith, LangFuse, Helicone, OpenLLMetry — emits these conventions natively and adds LLM-specific views: prompt diffing, eval-run dashboards, replay against an updated prompt or model, cost rollups by tag. The same data, exported in OTel format, also flows into ordinary observability backends, which means SREs see LLM traces in the same tool they already use for the rest of the system.

Senior tip · Make eval results a first-class artifact

Treat the JSON eval report from CI like a build artifact: store it next to the model version, link it from the registry record, and surface its summary in the PR description. Three months later, when someone asks "why did we ship v2.4 over v2.3?", the answer is one click away — not a forensic exercise across Slack threads.

A small Python snippet that emits an OTel-flavored span around a model call is short enough to fit on a card:

from opentelemetry import trace
tracer = trace.get_tracer("app.llm")

def call_model(client, model, messages):
    with tracer.start_as_current_span("gen_ai.chat") as span:
        span.set_attribute("gen_ai.system", "openai")
        span.set_attribute("gen_ai.request.model", model)
        resp = client.chat.completions.create(model=model, messages=messages)
        u = resp.usage
        span.set_attribute("gen_ai.usage.input_tokens", u.prompt_tokens)
        span.set_attribute("gen_ai.usage.output_tokens", u.completion_tokens)
        return resp.choices[0].message.content
PART 11

Multimodal & beyond text

When the input is no longer just text, the engineering surface grows — but most production patterns stay the same.

Vision-language models

Vision-language models (VLMs) accept interleaved text and image tokens and emit text. The open-weights ecosystem is anchored by LLaVA-style architectures (a vision encoder feeding a projection layer into an instruction-tuned LLM), with Qwen-VL and InternVL setting the practical bar on chart understanding, document QA, and grounded visual reasoning. On the hosted side, GPT-4o with vision, the Gemini family, and Claude with vision converge on a common API shape: a list of content parts where each part is either a text block or an image (URL, base64, or file ID).

The interface is uniform enough that you can write a single client wrapper and route across providers. Where they differ is in quality on specific subtasks (small text in diagrams, multi-page document layout, high-resolution detail extraction), in image-token economics (some bill per resized tile, others by total pixels), and in safety filters (faces, identifiable people, document fields). Pick by running your task against each on a representative held-out set; do not pick by leaderboard.

A minimal multimodal call looks the same across the major providers:

from openai import OpenAI
client = OpenAI()

resp = client.chat.completions.create(
  model="gpt-4o",
  messages=[{
    "role": "user",
    "content": [
      {"type": "text", "text": "Extract all line items as JSON."},
      {"type": "image_url",
       "image_url": {"url": f"data:image/png;base64,{img_b64}",
                     "detail": "high"}},
    ],
  }],
  response_format={"type": "json_object"},
)
print(resp.choices[0].message.content)

Visual document retrieval

Traditional document pipelines parse PDFs into text via OCR, chunk the text, and embed the chunks. The pipeline is brittle — OCR loses table structure, chart axes, and multi-column layouts — and tuning it across a heterogeneous corpus is a months-long exercise.

ColPali and the broader family of late-interaction visual retrievers ("page-image embeddings") flip the contract. Each PDF page is rendered as an image, passed through a vision encoder fine-tuned for retrieval, and stored as a small set of patch embeddings. Query text is embedded once; relevance is scored by a MaxSim-style late interaction across query tokens and page patches. In practice the approach delivers strong retrieval quality on visually-rich documents — invoices, financial reports, scientific papers with figures — without ever running OCR.

The trade is index size and storage cost. A page that previously embedded as a single 1024-dimensional vector now stores tens of patch vectors. The right pattern for most production systems: ColPali-style retrieval at the recall stage, then a VLM call on the top-k page images for grounded answer synthesis. If extracted structured data is also needed downstream, parse only the pages that the retriever surfaced — by then you have shrunk the OCR target by two orders of magnitude.

Key idea · Skip OCR when the model can read pixels

Before investing weeks in an OCR + layout-parser + table-detector pipeline, prototype a page-image-first retriever and a vision-capable answerer on the same corpus. The pixel-native path frequently wins on quality and ships in a fraction of the time. Reach for OCR when the answer must be structured data extracted from every page, not just the few the user asked about.

Speech and audio

Speech models split into three useful classes. Transcription (speech-to-text): Whisper-v3 remains the open-weights default for batch and near-real-time, with strong multilingual coverage. Hosted alternatives like Deepgram, AssemblyAI, and the major cloud APIs trade openness for lower word-error rates on phone audio and faster real-time streaming.

Audio understanding beyond raw transcription is now first-class: Voxtral and similar audio-language models accept raw audio plus a text instruction and emit text, which collapses transcribe-then-prompt pipelines into a single call and preserves prosodic cues (sarcasm, hesitation, speaker affect) that text loses. Speaker diarization (who-said-what) and audio embeddings (for clustering and retrieval) are usually still separate models that run in parallel.

Real-time speech-to-speech is the newest tier. Models that consume streaming audio frames and emit streaming audio frames — turn-taking, interruption handling, and prosody control built in — make conversational voice agents tractable without the latency stack-up of ASR → LLM → TTS. The engineering trade-off is loss of intermediate text: logging, evaluation, and content moderation must now operate on audio or on a parallel transcription stream.

Document AI and structured extraction

Layout-aware models (LayoutLM-family, DocLayout, Donut) bring positional information into the encoder, which matters for forms, tables, and any document where reading order is non-linear. Modern frontier VLMs increasingly subsume these tasks: a single prompt with a JSON schema and a page image often outperforms a hand-tuned layout pipeline, especially on the tail of formats where there is not enough labeled data to fine-tune a specialist.

For tables specifically, two patterns dominate in 2025-2026. The first is schema-driven extraction: hand the model a target JSON shape and the page image, validate the output against the schema, and retry on failure. The second is two-pass reconciliation: extract the table independently with two different methods (a layout parser and a VLM, say) and reconcile cells where they disagree. The second pass costs more but raises precision on financial and clinical data where a single misread cell is expensive.

Generation as a step inside an agent

Image and video generation models are increasingly invoked as tools by agentic systems rather than as user-facing endpoints. A document-drafting agent generates supporting illustrations; a marketing agent generates A/B-tested visuals from a brand spec; a video-editing agent synthesizes B-roll. The engineering implications mirror those of any other tool call: deterministic seeds where the model supports them, content-safety filtering on outputs, caching by prompt hash, and cost guardrails because image and video generations are typically an order of magnitude more expensive than a text completion. Treat generated assets as immutable artifacts in object storage, referenced by content hash, so a regenerated identical request returns the cached file rather than billing twice.

PART 12

System design playbook

The pieces are familiar — API tier, gateway, retrieval, observability — but the failure modes and the unit economics are not.

Reference architecture for a production LLM application

A workable production architecture has four tiers and a sidecar. The stateless API tier terminates user traffic, handles auth and tenant resolution, and forwards normalized requests inward. The model gateway centralizes prompt-template resolution, rate limiting, retries, fallbacks, and per-call telemetry. The retrieval and engines tier holds the vector index, lexical index, reranker, and the model runtime itself (hosted API, self-hosted vLLM/TGI, or both behind a chooser). The eval and observability sidecar samples traffic, runs online evals, and ships traces to the metrics store. A separate feedback store — discussed in prose below rather than drawn as a fifth tier — captures user signals into a typed event log that downstream jobs lift into eval suites and fine-tuning sets.

Statelessness in the API tier is non-negotiable for horizontal scaling. Conversation state lives in a session store keyed by conversation ID and refreshed on each turn; the API tier itself holds no per-user memory. The gateway exists to absorb provider quirks: it normalizes message shapes, retries on transient 5xx with jittered backoff, falls back to a secondary provider on hard failures, and short-circuits to cached responses on prompt-hash hits where appropriate.

Multi-tenancy, isolation, and quotas

Most LLM applications serve more than one tenant. Hard isolation — a separate stack per tenant — is reserved for regulated workloads (defense, healthcare with PHI, certain financial flows) where data co-mingling is unacceptable. The common case is logical isolation: a single shared stack with tenant ID propagated through every layer as a first-class request attribute, and storage partitioned by tenant.

Quotas operate at three levels. Per-tenant quotas cap requests-per-second and tokens-per-minute, sized by plan tier and enforced at the gateway. Model-level quotas protect upstream providers from saturation: a single misbehaving tenant cannot exhaust the global rate limit on the frontier model. Per-feature quotas guard against runaway internal jobs — a batch summarization that quietly enters an infinite retry loop should hit its own ceiling long before it eats the tenant's headroom. Token-bucket algorithms with redis-backed counters handle all three with one mechanism.

Scaling LLM workloads

Vertical scaling — bigger GPUs, more memory — runs into a wall fast. Frontier models already saturate H100/H200 nodes; the next step is multi-node tensor and pipeline parallelism, which is operationally heavier than most teams want. Horizontal scaling is the better default for serving: replicate the runtime behind the gateway, autoscale on a meaningful signal, and let the load balancer distribute work.

The signal worth autoscaling on is rarely CPU. Tokens-per-second throughput per replica and queue depth at the runtime are far better proxies for saturation. CPU is a misleading low-water mark on GPU-bound services; queue depth captures the moment when latency starts to blow out. A practical setup: scale up when sustained queue depth exceeds k requests per replica, scale down when queue depth has been zero for several minutes and replica count is above the floor.

Concurrency tuning at the runtime layer matters as much as replica count. Continuous-batching servers (vLLM, TGI, SGLang) extract substantially more throughput per GPU when max_num_seqs is sized to the workload's prompt-length distribution. Set it too low and the GPU sits idle; set it too high and KV-cache pressure causes preemption and tail-latency spikes. Profile against representative traffic, not against synthetic uniform-length prompts.

Pitfall · Average latency hides the tail

p50 latency on a continuous-batching server can stay flat while p99 doubles, because long-prompt outliers preempt shorter ones in the batch. Always autoscale and alert on p95 or p99 — not on the mean — and chart latency against prompt-length percentile to catch the failure pattern early.

Cost modeling: a worked example

The recurring decision in serving is hosted-API versus self-hosted. The break-even depends on three things: traffic volume, the model size you actually need, and the GPU you can keep busy. A small worked example sharpens the intuition.

Assume a chat workload with average prompt length 2,000 input tokens, average completion 400 output tokens, sustained 10 requests/second around the clock. Hosted-API option: a mid-tier model at $0.50 per million input tokens and $1.50 per million output tokens. Self-hosted option: an 8B model on a single H100-class GPU billed at $3.50/hour, throughput around 30 requests/second on the same prompt shape with continuous batching.

The arithmetic: 10 req/s × 86,400 s/day × 30 days ≈ 25.9 M requests/month. At 2,000 input tokens that is ≈ 51.8 B input tokens/month, costing 51,840 × $0.50 = $25,920. At 400 output tokens that is ≈ 10.4 B output tokens, costing 10,368 × $1.50 = $15,552. Hosted total ≈ $41,500. Self-hosted: two GPUs × $3.50/hour × 720 hours/month ≈ $5,040. The self-hosted option looks dramatically cheaper, but the comparison is honest only if the 8B open-weights model meets quality on this task. If it does not, the hosted bill is buying you capability you cannot replicate, and the right move is often a hybrid: route the easy traffic to the cheap path, escalate the rest.

The break-even traffic level where the two options cross is sensitive to one parameter more than any other: per-replica throughput. Continuous batching with appropriate max_num_seqs settings can lift the same hardware from 10 req/s to 50 req/s on the same prompt shape. Profile before purchasing reserved capacity.

The cost-latency frontier

Different serving choices occupy different points on a cost-latency Pareto curve. Naming the shape of the curve is more useful than memorizing absolute numbers, which move with every quarterly price update.

Reading the figure: edge small-language-models and self-hosted 8B-class runtimes occupy the cheap end with low-to-moderate latency, frontier hosted APIs anchor the expensive low-latency corner, and asynchronous batched inference sits in the deep-cheap, slow-response corner. A given product feature often blends two: a fast cheap path for routine traffic and an escalation to a frontier model for the long tail. The gateway tier is where that policy lives; encoded as a routing rule, it can be tuned without redeploying the application.

Senior tip · Cache-hit economics often dominate the spreadsheet

A 30 % prompt-cache hit rate on a workload with long shared system prompts can cut input-token cost by close to 30 % almost for free, because cached prefixes are billed at a fraction of full rate by most providers and at zero by self-hosted runtimes. Before re-architecting, instrument the prompt-hash cache rate end-to-end. Many "expensive workload" memos disappear after a stable system-prompt design and a small KV-cache front of the runtime.

A short routing rule that demonstrates the pattern — pick the cheapest model whose probability-of-success crosses a threshold, escalate otherwise:

def choose_model(prompt: str, ctx: dict) -> str:
    # Deterministic features the router is allowed to use
    n_in = len(ctx["tokens_in"])
    has_tools = bool(ctx.get("tool_calls"))
    is_code = ctx.get("intent") == "code"

    if is_code or has_tools or n_in > 8000:
        return "frontier-hosted"     # complex paths
    if n_in < 1500 and ctx.get("tier") == "free":
        return "edge-slm-3b"         # cheap path for short, low-tier
    return "self-host-8b"            # default: cheap and good enough

This design closes the loop: the gateway emits per-route success rates and costs to the observability sidecar (Figure 12.1); the routing thresholds are revised based on what the sidecar shows; the change is a config push, not a code release. The architecture is boring on purpose. It is the boring parts — clear tiers, statelessness, telemetry on every hop, a single place to change routing — that let teams iterate on prompts, models, and retrieval quality without stalling on infrastructure.
