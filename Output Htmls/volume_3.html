PART 7

Production engineering for LLM apps

Turning a working prompt into a system that streams, caches, fails over, and survives traffic — without melting the bill or the latency budget.

7.1 Streaming: SSE, WebSockets, and cancellation

For chat-style applications, perceived latency is dominated by time to first token, not total generation time. Streaming the output as the model produces it converts a multi-second wait into an interactive experience. Two transports dominate.

Server-Sent Events (SSE) is a simple, unidirectional, HTTP-based protocol. Each response is a long-lived text/event-stream in which the server emits data: {...}\n\n frames. Browsers expose it through EventSource; on the server side any framework that supports streaming responses works. SSE is the right default: it traverses load balancers and proxies cleanly, supports automatic reconnection with Last-Event-ID, and matches the half-duplex nature of token streaming. Both major commercial providers ship SSE for streaming chat completions.

WebSockets are full-duplex and stateful. They are appropriate when the client also pushes data during generation — voice agents that stream microphone audio, multi-modal interactive sessions, or live collaborative documents — and when sub-100 ms server-to-client signalling is needed. The cost is operational: WebSocket-friendly load balancing, per-connection memory, and reconnection logic.

Backpressure and cancellation

An LLM gateway sits between fast producers (the model) and slow consumers (the network plus the browser). Without backpressure, queues grow unbounded under load. In Python, asyncio.Queue with a maxsize applied between the upstream stream reader and the downstream sender forces the producer to await when the buffer is full. In Node, Readable streams handle this implicitly via the highWaterMark and pause/resume contract.

Cancellation is the dual problem. When a user closes the tab or hits stop, three things must happen quickly: the framework must observe the disconnect, propagate it to the upstream HTTP request, and stop the model. FastAPI exposes this via request.is_disconnected() or by catching asyncio.CancelledError inside the generator; httpx and aiohttp both abort the upstream socket when their async context exits. Browsers cancel fetch with an AbortController. The provider SDKs honour stream context-managers (Anthropic's client.messages.stream, OpenAI's streaming generator) so closing them server-side stops billing — confirm this on your provider, since stop tokens already incurred remain billed.

Pitfall · The "ghost stream"

It is easy to write a streaming endpoint that looks like it cancels but actually keeps draining the provider response in a detached task. Always tie the upstream HTTP client lifetime to the response generator scope, and verify under load that cancelled requests stop incurring token usage on your provider dashboard.

7.2 Caching: exact, semantic, and provider-side

LLM calls are expensive in latency and money; the cheapest token is the one you do not generate. Three caching strategies compose well.

Exact-match caching hashes the full request — model, system prompt, message list, sampling parameters — and stores the completion in Redis or similar. It is appropriate for deterministic prompts (low temperature, no randomness), repeated lookups, and idempotent transformations. The hit rate is typically modest in chat applications because user inputs vary, but high in classification, extraction, and tool-call workflows.

Semantic caching embeds the user query (or the canonicalised prompt minus the system part) and looks up nearest neighbours in a vector store. If cosine similarity exceeds a threshold — often ≥ 0.95, tuned on a labelled set — the cached completion is returned. This catches paraphrases ("what's the refund policy?" vs. "how do I get my money back?"). The risk is false positives: two queries with high embedding similarity that have different correct answers ("flight from Paris to London" vs. "flight from London to Paris"). Mitigations: aggressive thresholds, per-tenant or per-user namespacing, and always pairing the cache with a small online evaluator. GPTCache and the LangChain semantic-cache classes ship reasonable defaults; rolling your own with Redis Stack or a small embedding model is straightforward.

Provider-side prompt caching is a major 2024–2025 development. Anthropic's Claude API supports explicit cache_control breakpoints with five-minute (and one-hour beta) TTLs; OpenAI applies automatic prefix caching to prompts above approximately 1,024 tokens at a discount on cached input tokens; Google Gemini exposes an explicit context-caching API for storing large pinned contexts. The economics are striking: for a long system prompt or large retrieved corpus that does not change between turns, cached prefix reads cost a fraction of fresh input tokens, and latency improves because the KV cache is preserved server-side. Structuring prompts as [stable system | stable tools | stable retrieved context | volatile user turn] maximises the cacheable prefix.

7.3 Multi-provider routing and failover

A single-provider deployment is a single point of failure, both technical (regional outages, rate limits) and commercial (price changes, deprecations). A routing layer abstracts the provider behind a uniform API and adds operational policies on top. Three open-source or hosted layers see common production use:

  • LiteLLM — a thin Python client and proxy that exposes an OpenAI-compatible API for 100+ providers, with built-in fallbacks, retries, cost tracking, and a key-management layer suitable for multi-tenant gateways.
  • OpenRouter — a hosted aggregator: one API, one billing relationship, automatic failover across providers for the same model family.
  • Portkey — an "AI gateway" focused on observability, virtual keys, guardrails, and routing rules; positioned closer to a control plane than a library.

The two routing patterns that matter operationally are failover routing and cost-aware routing. Failover routes the next request to a secondary provider when the primary returns 5xx, 429, or exceeds a latency budget. Capability matching is essential: a tool-use prompt cannot transparently fail over to a model that does not support tool calls, and a JSON-mode call must fall back to a model with comparable structured-output guarantees. Cost-aware routing decides per request which model is "good enough" — small models for classification, summarisation, and routing; flagship models for synthesis and reasoning. Production deployments typically combine a small classifier (rules or a fine-tuned encoder) with a cost-vs-quality table; meta-routers such as RouteLLM and similar research-grade systems learn this routing policy directly from preference data.

7.4 Structured outputs

Most production LLM calls are not free-form chat: they extract entities, populate forms, choose tools, or emit machine-readable JSON. Three families of techniques exist to make this reliable.

Native JSON modes. OpenAI's response_format={"type": "json_schema", "json_schema": {...}, "strict": true} guarantees outputs valid against a JSON Schema; Anthropic and Gemini achieve the same effect through tool use, defining a tool whose input schema matches the desired structure and forcing the call. Native modes are cheapest, fastest, and most accurate when the schema is supported.

Constrained decoding. Libraries like Outlines, lm-format-enforcer, guidance, and the constrained-grammar features in vLLM mask the model's logits at each step so only tokens compatible with a regex, JSON Schema, or context-free grammar receive non-zero probability. This works for self-hosted models and provides hard guarantees, not soft hints. The cost is integration complexity and a small throughput penalty.

Validate-and-retry wrappers. Instructor (Pydantic + OpenAI/Anthropic) and similar frameworks parse outputs into a typed model, and on a validation error, re-call the LLM with the parser's exception text appended. This is robust, works with any provider, and integrates cleanly with Pydantic v2; the failure mode is the occasional infinite retry loop, so a hard cap (typically 2–3 attempts) and a fallback to a cheaper "extract again" prompt are non-negotiable.

7.5 Reliability: retries, idempotency, circuit breakers

LLM endpoints exhibit the failure modes of any high-traffic HTTP service plus a few of their own: token-budget rate limits (TPM/RPM), capacity throttling under demand spikes, and long-tail latencies that exceed normal HTTP timeouts. The reliability toolkit is the standard one, with one specifically-LLM twist.

Exponential back-off with jitter. Naive exponential back-off — sleep = base · 2^attempt — synchronises failed clients, which retry in lockstep and worsen the outage. Adding jitter breaks the synchronisation. The "full jitter" recipe — sleep ~ Uniform(0, base · 2^attempt) — is a well-studied default. Formally:

For attempt \(k \in \{0, 1, 2, \dots\}\), the delay is

$$\Delta_k \sim \mathrm{Uniform}\!\left(0,\; \min(c,\; b \cdot 2^{k})\right)$$

where \(b\) is the base delay (e.g. 250 ms) and \(c\) is a hard cap (e.g. 30 s) to keep the worst-case wait bounded. Always honour Retry-After when the server sets it; it overrides your jitter schedule.

Idempotency. Both Anthropic and OpenAI accept an Idempotency-Key header on POST requests; the server deduplicates by key for a window of minutes to hours. The client generates a UUID once per logical request and reuses it across retries. Without this, a retry after a server-side success but before the response reaches the client double-bills and double-acts (especially dangerous for tool-using agents that perform side effects).

Circuit breakers. When the downstream provider is degraded, hammering it with retries is counterproductive. A circuit breaker counts failures in a sliding window; once a threshold is exceeded, it opens and short-circuits subsequent calls (returning a cached response, a graceful fallback, or a friendly error) for a cool-down. After the cool-down, a single half-open probe tests recovery. The pattern composes cleanly with multi-provider routing: when the primary breaker opens, traffic shifts to secondary.

Rate-limit handling. Provider rate limits are token-based (TPM) and request-based (RPM). Client-side, a token-bucket limiter aware of both dimensions prevents 429s from leaving your process. Server-side, a global queue with per-tenant fairness keeps a noisy neighbour from starving others.

7.6 Token budgeting

Even with million-token context windows, naïve "append every turn" strategies degrade quality, latency, and cost. Three techniques manage the budget:

  • Conversation windowing keeps the last \(K\) messages or last \(N\) tokens, with the system prompt sticky.
  • Summarisation compression rolls older history into a running summary once the window crosses a threshold; the summary becomes the first user-visible memory entry.
  • Sliding-window with anchors keeps the system prompt, the most recent \(K\) turns, and explicitly anchored memories (pinned facts, retrieved entities) — discarding the unstructured middle.

A practical observation: effective context is shorter than advertised. Needle-in-a-haystack benchmarks show meaningful degradation past the middle of long contexts for many models, and reasoning quality drops well before the hard limit. Prompt compression libraries such as LLMLingua and LongLLMLingua apply learned compression to non-essential prompt regions and report 5×–20× compression with modest quality loss; useful when latency or cost is the binding constraint.

Streamed FastAPI proxy with full-jitter retry on transient errors.

import asyncio, random, httpx
from fastapi import FastAPI, Request
from fastapi.responses import StreamingResponse

app, LLM_URL, AUTH = FastAPI(), "https://api.provider.example/v1/chat", {"Authorization": "Bearer ..."}

async def stream_with_retry(payload, max_retries=4, base=0.25, cap=8.0):
    for attempt in range(max_retries):
        try:
            async with httpx.AsyncClient(timeout=60) as client:
                async with client.stream("POST", LLM_URL, json=payload, headers=AUTH) as r:
                    r.raise_for_status()
                    async for chunk in r.aiter_bytes():
                        yield chunk
            return
        except (httpx.HTTPStatusError, httpx.TransportError):
            if attempt == max_retries - 1: raise
            await asyncio.sleep(random.uniform(0, min(cap, base * 2 ** attempt)))

@app.post("/chat")
async def chat(req: Request):
    body = await req.json()
    return StreamingResponse(stream_with_retry(body), media_type="text/event-stream")
Senior tip · Where to put each defence

Idempotency keys belong on the outermost retry boundary. Caches belong inside the gateway, before retry logic. Circuit breakers wrap each provider, not the gateway. Token-bucket limiters live at the edge of your service, not your provider's. Mixing these up is the most common cause of mysterious "we keep paying but the user sees errors" incidents.

PART 8

Evaluation

Benchmarks tell you about a model, evaluations tell you about a system — and the gap between the two is where most production failures live.

8.1 Standard benchmarks: what they actually measure

Public benchmarks anchor model comparisons but rarely predict task-specific quality. A working knowledge of what each one tests — and where it fails — is needed to read provider claims critically.

Contamination. Most public benchmarks have been ingested into pre-training corpora, sometimes inadvertently. Headline scores on heavily-contaminated sets thus over-state real ability, especially for older datasets. Contamination-resistant benchmarks (LiveBench, LiveCodeBench, freshly written QA suites) periodically rotate items to mitigate this; pair them with public sets and report both.

8.2 Human preference at scale

Chatbot Arena is the most cited human-preference signal: anonymous pairwise votes between two models on user-supplied prompts, aggregated with Bradley–Terry / Elo into a leaderboard. It correlates broadly with what feels good to use, captures aspects (tone, formatting, conciseness) that benchmarks miss, and is hard to game in the short term.

It is also limited. Arena votes skew toward casual prompts, reward verbose and well-formatted answers, and rarely measure factual correctness directly. The "style-controlled" leaderboards published by the same group attempt to control for length and Markdown formatting, with noticeable effects on rankings. Treat preference scores as one signal — alongside benchmarks and your own task-specific evals — not as the ground truth.

8.3 Designing task-specific evaluations

The single highest-leverage engineering investment in an LLM application is a small, well-curated, task-specific evaluation suite. A good suite has four properties.

Golden sets

A hand-curated collection of 50–500 input/output pairs anchored in real or carefully synthesised user behaviour. Curate diversity along the axes that matter — input length, language, user intent, edge cases, adversarial inputs — not by uniform random sampling from logs. Each example carries an oracle answer or, for open-ended tasks, an oracle specification against which a judge can score outputs.

Regression suites and slices

The golden set runs on every release, every prompt change, every model swap. Sliced metrics — mean accuracy on long-input examples, on Spanish prompts, on examples flagged as hard, on each user segment — surface regressions that aggregate scores hide. A 1 % overall improvement that masks a 10 % drop on a critical slice is a regression.

Statistical significance and power

With \(N\) examples and observed accuracies \(p_1, p_2\) on systems A and B evaluated on the same prompts, the paired McNemar test or paired bootstrap is the right framing — not a two-proportion z-test, which assumes independence. To detect a minimum effect \(\delta\) at significance \(\alpha\) and power \(1-\beta\), required sample size scales roughly as

$$N \approx \frac{(z_{1-\alpha/2} + z_{1-\beta})^2 \, \sigma^2}{\delta^2}$$

where \(\sigma^2\) is the variance of the per-example score difference. In practice, golden sets of 100–300 give credible signals on shifts of a few percentage points; smaller sets are still useful for direction-of-change but not for confidence intervals.

8.4 Synthetic evaluation generation

Hand-curating eval data is expensive, so practitioners generate it with strong LLMs: prompts, oracle answers, and adversarial variants alike. Self-Instruct, Evol-Instruct, and similar pipelines automate this. The technique is genuinely useful — it expands coverage to long-tail intents quickly — but introduces a circularity: the model that generates the eval is often correlated with the model under test, and a strong-model judge that scores outputs may share blind spots with both.

Mitigations: use a generator from a different model family than the system under test; spot-check a stratified sample by hand; pair every synthetic split with a human-curated split; and never use synthetic eval as the sole signal for go/no-go decisions.

8.5 LLM-as-judge

Hand-grading hundreds of open-ended outputs per release does not scale. Using an LLM as a judge — given the input, the output, and a rubric or reference, return a score or a winner — does. Common patterns:

  • Pairwise. Show two outputs; the judge picks A, B, or tie. The simplest and best-calibrated form.
  • Single-grade. Show one output; the judge scores it on a rubric (1–5 or per-dimension).
  • G-Eval. Use chain-of-thought plus a structured form-filling prompt to reduce variance and surface justifications.
  • MT-Bench. A standard multi-turn benchmark with an LLM judge; widely used for chat-quality smoke tests.

LLM judges have well-characterised biases. Position bias: they prefer the first option in pairwise comparisons; mitigate by running each pair twice with order swapped and averaging. Length bias: they prefer longer, more verbose answers; mitigate with length-controlled rubrics or by reporting length-adjusted scores. Self-preference bias: judges from a given model family rate outputs from that family more favourably; mitigate by judging with at least two distinct families and checking inter-judge agreement. Formatting bias: bullet-pointed and Markdown-heavy answers score higher even when content is equivalent.

8.6 RAG evaluation

Retrieval-augmented systems have a richer failure surface than plain generation: bad retrieval, good retrieval the model ignores, good retrieval the model misuses, hallucinated grounding. The standard four-metric decomposition separates retrieval quality from generation quality.

  • Faithfulness. Are the claims in the answer entailed by the retrieved context? Computed by extracting claims from the answer and verifying each against the context.
  • Answer relevance. Does the answer address the question asked, regardless of whether it is grounded? Often computed by generating questions from the answer and measuring similarity to the original.
  • Context precision. Among the retrieved chunks, are the relevant ones ranked high? Standard ranking metric.
  • Context recall. Is all the information needed to answer present in the retrieved set? Requires a ground-truth answer.

Three libraries dominate the open-source space: RAGAs (the canonical RAG-metrics toolkit), TruLens (instrumentation plus a "feedback functions" abstraction), and Arize Phoenix (tracing, evals, and a browser UI). All three integrate with common framework tracers (LangChain, LlamaIndex, OpenTelemetry) and can run in CI.

Computing two RAGAs metrics on a small toy dataset.

from datasets import Dataset
from ragas import evaluate
from ragas.metrics import faithfulness, answer_relevancy

samples = {
    "question":     ["Where is the European Central Bank headquartered?"],
    "answer":       ["The ECB is headquartered in Frankfurt am Main."],
    "contexts":     [["The European Central Bank is based in Frankfurt am Main, Germany,"
                      " and supervises euro-area banks."]],
    "ground_truth": ["Frankfurt am Main, Germany"],
}
dataset = Dataset.from_dict(samples)

result = evaluate(dataset, metrics=[faithfulness, answer_relevancy])
print(result.to_pandas()[["faithfulness", "answer_relevancy"]])

8.7 Agent evaluation

Agent systems add a temporal dimension: success depends on a sequence of decisions, tool calls, and recoveries. Three layers of evaluation apply.

Trajectory evaluation compares the actual tool-call sequence and intermediate states against a reference trajectory or a graded specification. Useful when the task has multiple acceptable solution paths but constrained ones.

Tool-call accuracy grades each individual call: was the right tool selected, were the arguments well-formed and correct, was the result correctly interpreted? It catches schema-confusion bugs that end-to-end metrics hide.

End-to-end success measures task completion against ground-truth outcomes. Public benchmarks include SWE-bench and SWE-bench Verified (real GitHub issues plus tests), WebArena and VisualWebArena (browsing tasks), and OS-World (computer-use). They are useful baselines but rarely match your domain; build a small in-domain end-to-end set as well.

8.8 Online evaluation

Offline scores predict, online metrics decide. The standard online instruments:

  • Shadow traffic. Mirror a slice of production requests to a challenger system without returning its response to users; compare offline. Cheap, safe, and the right first step.
  • A/B tests with feature flags. Randomly assign users to control and treatment; track conversion, engagement, retention, and direct LLM-quality signals (regeneration rate, edit distance from response, thumbs).
  • Win-rate and regret. For systems that can ship two outputs, present both (or interleave) and let preferences speak. Regret tracks the cumulative loss from suboptimal choices over time.
  • User-feedback loops. Thumbs, free-text feedback, "regenerate" clicks, and edit telemetry compose into a noisy but high-volume quality signal. Pair with a sampled human-graded subset to anchor calibration.
Pitfall · Goodhart on user signals

Optimising directly to thumbs and engagement reliably produces longer, more confident, more sycophantic answers — not better ones. Treat online signals as a check on offline evaluation, not a substitute for it, and audit drift in answer length, hedging, and refusal rates over time.

PART 9

Safety, security, responsible AI

The model is a programmable component reachable by anyone whose data ever touches it — so the threat model has to expand to match.

9.1 Threat model

An LLM application surface differs from a traditional web service in one crucial respect: the same channel that carries user intent also carries instructions the model will execute. Any text reaching the prompt — directly typed, retrieved, scraped from a tool result, embedded in a PDF or image — is potentially adversarial.

Direct prompt injection. The user types instructions intended to override the system prompt or extract secrets ("ignore previous instructions and …"). Effective for systems with weak system-prompt isolation, secret data in the system prompt, or under-constrained tools.

Indirect prompt injection. An attacker plants instructions in content the model will later read — a webpage, an email, a calendar invite, a document in a corporate share, an image alt-text, a vector-store record. When the agent reads that content, it executes the injected instructions on the original user's behalf and authority. This is the most consequential class of LLM attack and the hardest to fully mitigate.

Jailbreaks. Inputs that elicit content the model is policy-trained to refuse — multi-turn role play, encoded payloads, "Crescendo"-style gradual escalation, low-resource-language requests, persona attacks. Distinct from injection: jailbreaks subvert the model's policy; injection subverts the system's policy.

Data exfiltration. The model emits sensitive data — system-prompt contents, retrieved documents, tool outputs, customer PII — into a channel the attacker controls. With tools, this includes constructing a URL with the secret in a query parameter and asking the agent to fetch it.

Tool abuse and excessive agency. An agent calls destructive tools (delete, send-email, transfer-funds) it should not have, with arguments derived from attacker-controlled context. The root cause is almost always over-broad tool grants combined with insufficient authorisation checks at the tool layer.

Model and supply-chain attacks. Compromised model weights, poisoned fine-tuning data, malicious adapters published on public hubs, typo-squatted package names. The mitigations are familiar from software supply-chain security: pin versions, verify checksums, prefer signed releases, and treat third-party adapters as untrusted code.

9.2 Defences

No single defence is sufficient. The mature posture is defence-in-depth across four layers.

Input guardrails classify or rewrite incoming prompts before the model sees them. Open-source options include Meta's Prompt Guard 2 (small classifier for jailbreak / injection detection), Rebuff (heuristics + canary-token approach), and the input-rail layer of NVIDIA's NeMo Guardrails. Commercial gateways (Portkey, Guardrails AI) bundle similar checks behind a single API.

Structural defences reduce the blast radius even when injection succeeds. Treat retrieved content and tool outputs as data, not instructions by tagging them with delimiters the system prompt explicitly refuses to follow. Run untrusted content under a model with constrained tool scope ("planner / executor" or "dual-LLM" patterns). Authorise every tool call at the tool boundary against the original user identity, not the model's request — the model is acting as a confused deputy.

Output guardrails classify or filter responses before they reach users or downstream systems. Llama Guard 3 and successors are content-policy classifiers from Meta released for this purpose; Guardrails AI validates structured output (PII presence, schema, safe SQL); the output rails in NeMo Guardrails compose programmable post-checks. Enforce schema, citation, and topicality constraints at this layer rather than trusting the model to self-police.

Tool sandboxing closes the last mile. Sensitive tools require human-in-the-loop confirmation; destructive operations are constrained to allow-listed targets; outbound HTTP fetches go through a egress proxy with denied internal addresses; secret values never enter the prompt at all (the tool reads them server-side from the user's vault).

9.3 PII handling and content policy

Logs and stored conversations are the most overlooked PII surface. Prompts often contain names, emails, addresses, account identifiers, and freely-typed health or financial details. Treat the log pipeline as a data-protection problem from day one: detect and redact at ingestion, not at query time.

Microsoft's open-source Presidio ships NER-based detectors and configurable redaction operators, including consistent aliasing — replacing identifiers with stable placeholders so referential structure survives ("PERSON_017 emailed PERSON_017 again") for analysis without exposing identity. Pair Presidio with format-preserving tokenisation for fields that downstream systems must round-trip. For training corpora, differentially-private fine-tuning (DP-SGD, opacus) provides quantitative guarantees but with measurable utility cost; reserve it for the most sensitive deployments.

9.5 Bias, toxicity, and provenance

Bias and toxicity evaluation suites — BBQ, BOLD, ToxiGen, DiscrimEval, StereoSet — measure disparate behaviour across demographic groups, refusal patterns, and toxic-completion rates. Useful in pre-launch evaluation; not a substitute for in-domain audits, since aggregate scores rarely surface failures specific to a particular product context.

Provenance and citation enforcement matter more than they used to. RAG systems can require every claim to map to a retrieved chunk, and refuse or abstain otherwise. Watermarking research (the Aaronson scheme, the Kirchenbauer green-list approach for text; Google's SynthID for image and increasingly for text) embeds detectable signals into outputs — useful for downstream provenance checks, with the caveat that paraphrase, translation, and short outputs degrade detection.

9.6 Compliance touch-points

GDPR. Prompt and completion logs typically contain personal data, which makes the logging pipeline a processing activity in its own right. Establish a lawful basis (usually legitimate interest plus contractual necessity for service-improvement; consent for training on user data), publish retention periods, honour data-subject access and erasure requests against the log store, and respect regional data-residency where applicable. The right-to-erasure obligation extends to fine-tuning corpora derived from user data.

HIPAA. US healthcare data (PHI) requires a Business Associate Agreement with any party that processes it. The major providers offer HIPAA-eligible deployments — OpenAI's enterprise tier, Microsoft Azure OpenAI, AWS Bedrock, Anthropic on supported clouds — but only under specific configurations (no training on data, no human review, regional endpoints). Verify the exact contractual surface before sending PHI.

SOC 2 Type II. The standard third-party assurance for SaaS controls. Vendor SOC 2 reports cover their controls, not yours; a SOC 2 attestation from a model provider lets your auditors check the box on vendor management but says nothing about how your application uses the model. Map your own controls to your trust-services criteria separately.

9.7 Governance artefacts

Model cards document a model's intended use, training data summary, evaluation results, known limitations, and demographic-disparity findings. System cards document the deployed application: prompts in use, tools and their permissions, eval results on the task, the safety stack, and known residual risks. Dataset cards document training and evaluation corpora — provenance, sampling methodology, known biases, licensing.

Two frameworks set the wider governance frame.

NIST AI Risk Management Framework organises AI governance under four functions — GOVERN, MAP, MEASURE, MANAGE — and its companion Generative AI Profile tailors the framework to LLMs and similar systems. It is a voluntary framework but the canonical reference cited in US federal procurement and increasingly in vendor questionnaires.

EU AI Act. Phased into force from 2025–2027, it imposes obligations on general-purpose AI providers (technical documentation, training-data summary, copyright policy, model evaluations; additional obligations for "systemic risk" models above a compute threshold) and on deployers of high-risk AI systems (risk management, data governance, logging, human oversight, post-market monitoring, conformity assessment, registration). Most engineer-facing applications are not themselves high-risk, downstream obligations cascade in regulated sectors — credit, education, public-sector decisions, biometric identification — where high-risk obligations apply. The Act treats this as engineering work — not a legal afterthought — and the documentation, logging, and evaluation practices in this volume are the same artefacts conformity assessment will require.

Senior tip · Build the artefacts as you build the system

Model cards, system cards, and risk registers written at launch are forensic documents at best. Maintained as living artefacts — updated each release alongside evals — they become the spine of incident response, regulatory audit, and onboarding for new engineers. The cost of writing them in tandem with the code is small; the cost of reconstructing them under deadline is enormous.
